# Project Spec: Rent Roll & Maintenance Hub

## Purpose

A small Python back end for a fictional apartment portfolio. Rent Roll & Maintenance Hub imports a property-management export, stores it in SQL Server, serves it through a FastAPI REST API, produces a formatted Excel rent roll and delinquency report on a schedule, and uses the Claude API to triage maintenance requests.

## Scope

The users are an internal property-operations team. The system is API-first, with no front end.

**User stories**

1. As a property accountant, I import the nightly property-management CSV export with one command, and re-running it never creates duplicates.
2. As a regional manager, I get an Excel rent roll and a delinquency aging report (0–30, 31–60, 61–90, 90+ days) every morning without asking anyone.
3. As a maintenance coordinator, I submit a work order and it arrives already tagged with a category and urgency that I can override.
4. As a developer on the team, I can call documented REST endpoints for properties, units, leases, balances and work orders.
5. As a reviewer, I can see from tests and CI that a change works before it merges.

**In scope**

- 3 properties, about 150 units, and 12 months of synthetic charges and payments, generated by a seed script with Faker
- CSV import, REST API, Excel reports, nightly Azure Function, AI ticket triage
- API-key authentication on write endpoints

**Out of scope (stretch only)**

- A front end
- Real property-management system connectivity or real resident data
- User accounts, roles and OAuth
- Payment processing

## Architecture and data model

One SQL Server database sits at the center. The import CLI and the nightly function write to it or read from it directly, and the FastAPI service is the only thing clients talk to. Shared logic (`services/`, `reports/`) is a plain Python package that all three entry points import.

CSV data flows in through the CLI, reports flow out through the function, and triage is a side call the API makes when a work order is created.

**Schema (8 tables, 1 view, 1 stored procedure)**

| Object | Key columns | Notes |
| --- | --- | --- |
| `properties` | property\_id, name, city | 3 seeded properties |
| `units` | unit\_id, property\_id → properties, unit\_number, bedrooms, market\_rent, status | Unique (property\_id, unit\_number) |
| `residents` | resident\_id, first\_name, last\_name, email | Synthetic data only |
| `leases` | lease\_id, unit\_id → units, resident\_id → residents, start\_date, end\_date, monthly\_rent | Index on (unit\_id, end\_date) |
| `ledger_entries` | entry\_id, lease\_id → leases, entry\_date, entry\_type, amount DECIMAL(10,2) | entry\_type CHECK: charge, payment, late\_fee; index on (lease\_id, entry\_date) |
| `work_orders` | work\_order\_id, unit\_id → units, description, category, urgency, ai\_category, ai\_urgency, triage\_source, status, created\_at | AI values kept beside human overrides |
| `import_log` | import\_id, file\_name, rows\_read, inserted, updated, rejected, started\_at, duration\_ms | Audit trail for every import |
| `stg_import` | Raw columns from the CSV | Truncated at the start of each import |
| `vw_rent_roll` | One row per occupied unit with current lease and balance | View, used by API and Excel |
| `usp_delinquency_report` | `@as_of_date DATE` | Stored procedure; buckets balances 0–30/31–60/61–90/90+ with `CASE` + `DATEDIFF` |

The view and the stored procedure are written in raw T-SQL inside Alembic migrations, not through the ORM.

## API endpoints

Ten endpoints under `/api/v1`, documented automatically at `/docs`. Write endpoints require an `X-API-Key` header.

| Method | Path | Does | Notes |
| --- | --- | --- | --- |
| GET | `/health` | Liveness plus a database ping | Used by CI and the deploy |
| GET | `/properties` | List properties with unit count and occupancy % | Aggregate query |
| GET | `/properties/{id}/units` | Units with current resident and lease end | Filters: `status`, `bedrooms` |
| GET | `/leases/{id}/ledger` | Charges and payments with running balance | Window function (`SUM() OVER`) |
| GET | `/reports/rent-roll` | Rent roll as JSON | Reads `vw_rent_roll` |
| GET | `/reports/delinquency` | Aging buckets per resident | Calls `usp_delinquency_report @as_of_date` |
| GET | `/reports/delinquency.xlsx` | Same report as a formatted Excel download | `StreamingResponse` |
| POST | `/work-orders` | Create a work order; AI triage fills category and urgency | Returns `201` with triage result |
| PATCH | `/work-orders/{id}` | Human override of category, urgency or status | Keeps the AI's original values |
| GET | `/work-orders` | List work orders, filter by `property_id`, `urgency`, `status` | Paginated (`limit`, `offset`) |

**Conventions:** Pydantic request and response models for every route; `404` and `422` errors with a consistent JSON body; pagination on every list; no business logic in route functions (it lives in a `services/` layer that tests call directly).

## Automation features

Each should be demoable in under a minute.

**1. CSV import CLI** — `python -m hub import data/export_2026-11-23.csv`

- Built with Typer. Reads the export with pandas, validates each row with a Pydantic model, and reports bad rows with line numbers instead of crashing.
- Loads valid rows into a staging table, then runs one T-SQL `MERGE` inside a transaction. Re-running the same file changes nothing (idempotent).
- Writes a row to `import_log`: file name, rows read, inserted, updated, rejected, duration.
- A `--dry-run` flag shows what would change without committing.

**2. Excel reports (pandas + openpyxl)**

- Rent roll sheet: property, unit, resident, lease start/end, market rent, actual rent, balance.
- Delinquency sheet: one row per resident with 0–30 / 31–60 / 61–90 / 90+ buckets.
- Formatting: frozen header row, currency formats, auto-fit columns, conditional formatting that highlights 90+ in red, and live `SUM` formulas in the totals row.
- One `build_workbook(as_of_date)` function shared by the API download and the nightly job.

**3. Nightly Azure Function**

- Timer trigger at 6:00 AM Mountain (CRON in UTC). Calls `build_workbook(today)` and uploads `delinquency_YYYY-MM-DD.xlsx` to a Blob Storage container.
- Connection strings come from app settings, never from code. Logs row counts and duration.
- Fallback: an equivalent GitHub Actions scheduled workflow.

**4. AI maintenance triage (Claude API)**

- On `POST /work-orders`, send the description to Claude with a short system prompt and ask for JSON: `category` (plumbing, electrical, HVAC, appliance, pest, general), `urgency` (emergency, high, normal, low) and a one-line `reason`.
- Validate the reply with a Pydantic model. If the call fails, times out or returns bad JSON, fall back to keyword rules and mark `triage_source = 'rules'`. The request never fails because the AI did.
- Store the AI's original values next to any human override so agreement rate can be reported.
- Tests mock the Anthropic client. One optional, marked test (`pytest -m live`) hits the real API.
- A 20-example labeled set and a script that reports accuracy.

## Testing, CI and Git workflow

**Tests (pytest)**

- Unit tests for validation, aging-bucket math, triage fallback rules and workbook building. The workbook test opens the generated file with openpyxl and checks headers, totals formulas and formats.
- Integration tests against a real SQL Server: the import is idempotent, `MERGE` updates changed rows, the stored procedure returns correct buckets for a hand-built fixture, and the API returns `404`/`422` correctly.
- Fixtures create a fresh schema per test session, and each test rolls back its own transaction.
- Target 80%+ coverage, reported in CI.

**CI (GitHub Actions)**

- On every PR: ruff check, ruff format check, Alembic migrations against a `mcr.microsoft.com/mssql/server:2022-latest` service container, then pytest with coverage.
- Branch protection on `main`: PR required, CI must pass, no direct pushes.
- A status badge in the README.

**Git workflow**

- One GitHub issue per feature, grouped into two milestones.
- One branch and one PR per issue. Each PR description covers what changed, why, how it was tested, and sample output where useful.
- A PR template with a self-review checklist: tests added, no secrets, migrations reversible, AI-generated code read line by line.
- Conventional commit messages (`feat:`, `fix:`, `test:`).
